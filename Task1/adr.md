# Архитектурное решение (ADR): Выбор стека технологий для RAG-бота QuantumForge Software

## Контекст
Компания QuantumForge Software разрабатывает интеллектуального бота для быстрого и персонализированного доступа к корпоративной базе знаний (≈ 18 000 Markdown/MDX, ≈ 3 000 страниц Confluence, ≈ 250 PDF). Цели: сокращение времени поиска информации, автоматизация рутинных запросов, выявление пробелов в документации и масштабирование решения. Объём прироста — около 400 страниц в месяц. Проблемы: разрозненность данных, дублирование, устаревание контента, длительный поиск (до 4 часов в неделю на сотрудника).

## Ограничения и требования
- **Конфиденциальность**: часть материалов (Terraform state, внутренние спецификации) не должна покидать инфраструктуру компании.
- **Масштабируемость**: решение должно поддерживать рост данных и нагрузку.
- **Интеграция**: необходимо работать с разными источниками (Confluence, GitHub, PDF, Google Drive).
- **Стоимость**: важно оптимизировать затраты на инфраструктуру и эксплуатацию.

## Анализ вариантов

### 1. Сравнение LLM-моделей
| Критерий                | Локальные (Hugging Face)                       | Облачные (OpenAI/YandexGPT)                  |
|-------------------------|------------------------------------------------|----------------------------------------------|
| **Качество ответов**     | Зависит от модели; современные (Llama 3, Mixtral) сопоставимы с GPT-4 | Высокое, особенно у GPT-4 Turbo              |
| **Скорость работы**      | Зависит от железа; возможны задержки на CPU   | Высокая, стабильная                          |
| **Стоимость**            | Капитальные затраты на железо + электричество | Операционные (токены); дорого при высокой нагрузке |
| **Простота развёртывания** | Сложнее, требует настройки инфраструктуры      | Проще, API-доступ                            |
| **Конфиденциальность**   | **Полная**, данные не покидают периметр        | Данные передаются третьей стороне            |

**Вывод**: Для конфиденциальных данных — только локальные модели. Для неконфиденциальных частей можно гибридный подход.

**Причины выбора локальных моделей**:
1. **Требования конфиденциальности**: В описании указано, что часть материалов является конфиденциальной (Terraform state, внутренние спецификации). Передача таких данных в сторонние облачные сервисы неприемлема с точки зрения безопасности.
2. **Контроль над инфраструктурой**: Локальное развёртывание позволяет полностью контролировать производительность, доступность и обновления системы.
3. **Долгосрочная экономия**: При высокой нагрузке (сотни/тысячи запросов в день) локальные модели становятся экономически выгоднее облачных API.

### 2. Сравнение моделей эмбеддингов
| Критерий                | Локальные (Sentence-Transformers)              | Облачные (OpenAI Embeddings)                 |
|-------------------------|------------------------------------------------|----------------------------------------------|
| **Скорость индексации**  | Быстрая на GPU, медленнее на CPU              | Зависит от API, лимиты на запросы            |
| **Качество поиска**      | Хорошее (например, all-MiniLM-L6-v2)           | Отличное (text-embedding-3-small/large)      |
| **Стоимость**            | Бесплатно после развёртывания                  | Плата за токены, может быть значительной     |
| **Конфиденциальность**   | **Полная**                                     | Данные уходят в облако                       |

**Вывод**: Для полного контроля и экономии — локальные эмбеддинги.

**Причины выбора Sentence-Transformers**:
1. **Согласованность с выбором LLM**: Если основная модель работает локально, имеет смысл и эмбеддинги держать локально для минимизации внешних зависимостей.
2. **Нулевая стоимость при инференсе**: После первоначальной настройки генерация эмбеддингов не требует дополнительных платежей.
3. **Гибкость выбора моделей**: Можно выбрать модель, оптимальную для технической документации (например, специализированные модели для кода или научных текстов).

### 3. Сравнение векторных БД
| Критерий                | ChromaDB                                       | FAISS                                         |
|-------------------------|------------------------------------------------|----------------------------------------------|
| **Скорость поиска**      | Хорошая, оптимизирована под RAG                | Очень высокая, библиотека от Facebook Research |
| **Скорость индексации**  | Средняя                                        | Высокая                                      |
| **Сложность внедрения**  | Низкая, встроенная поддержка эмбеддингов      | Средняя, требуется больше кода для управления |
| **Удобство работы**      | Высокое, REST API, клиенты для Python/JS      | Низкое, только Python-библиотека             |
| **Стоимость владения**   | Низкая (легковесная, можно развернуть в K8s)  | Низкая (библиотека, но требует отдельного хранилища метаданных) |
| **Масштабируемость**     | Горизонтальное масштабирование через репликацию | Только вертикальное, ограничено одной нодой   |

**Вывод**: ChromaDB — лучше для production-среды благодаря API, управлению метаданными и интеграциям.

**Причины выбора ChromaDB**:
1. **Производственная готовность**: ChromaDB создавалась именно для RAG-приложений, имеет встроенные функции для управления коллекциями, фильтрации и метаданными.
2. **Горизонтальное масштабирование**: Поддержка репликации и шардинга через встроенные механизмы или Kubernetes, что критично для роста данных компании.
3. **Удобство разработки и эксплуатации**: REST API позволяет легко интегрировать бота с другими системами (Slack, веб-интерфейс), а также упрощает мониторинг и управление.

### 4. Конфигурация сервера для RAG-бота
Для локального развёртывания модели (например, Llama 3 8B в 4-битной квантизации) и ChromaDB:

**Минимальная конфигурация (тестирование/разработка)**:
- **CPU**: 8 ядер (Intel Xeon или AMD EPYC)
- **RAM**: 32 GB DDR4
- **GPU**: NVIDIA T4 (16 GB VRAM) или эквивалент
- **Хранилище**: 256 GB NVMe SSD
- **Сеть**: 1 Gbps

**Рекомендуемая конфигурация (production, 100+ одновременных пользователей)**:
- **CPU**: 16+ ядер (Intel Xeon Gold 6338 или AMD EPYC 7543)
- **RAM**: 64+ GB DDR4 ECC
- **GPU**: 1× NVIDIA A10 (24 GB VRAM) или A100 (40/80 GB VRAM)
- **Хранилище**: 1+ TB NVMe SSD (RAID 1 для отказоустойчивости)
- **Сеть**: 10 Gbps

**Обоснование параметров**:
1. **GPU с большим объёмом VRAM**: Современные LLM (8B+ параметров) в полной точности требуют 16+ GB VRAM. Квантизация (4-bit) уменьшает требования, но для качественных эмбеддингов и одновременной обработки нескольких запросов нужен запас.
2. **Большой объём RAM**: Помимо модели в памяти, необходимо место для:
   - Операционной системы и сервисов
   - Векторной БД (кеширование)
   - Обработки документов при индексации
3. **Быстрое хранилище**: Индексация тысяч документов — IO-intensive операция, NVMe SSD ускорит процесс в 5-10 раз по сравнению с HDD.
4. **Сетевая пропускная способность**: При распределённой архитектуре (отдельные ноды для LLM, эмбеддингов и БД) нужна быстрая сеть для минимизации задержек.

## Варианты решения

### Вариант 1: Полностью локальный (максимальная безопасность)
- **LLM**: Llama 3 8B (4-bit) 
  - *Причина выбора*: Хороший баланс качества и требований к ресурсам, открытая лицензия, поддержка сообщества
  - *Железо*: NVIDIA A10 (24 GB VRAM) или RTX 4090 (24 GB)
- **Эмбеддинги**: all-MiniLM-L6-v2 (Sentence-Transformers)
  - *Причина выбора*: Быстрая, с хорошим качеством для технических текстов, малые требования к памяти
  - *Железо*: Может работать на CPU, но GPU ускорит в 10+ раз
- **Векторная БД**: ChromaDB в Kubernetes (EKS)
  - *Причина выбора*: Интеграция с существующей инфраструктурой AWS, масштабируемость
  - *Железо*: Отдельные ноды: 8 CPU, 16 GB RAM, быстрый SSD
- **Плюсы**: Полная конфиденциальность, предсказуемая стоимость.
- **Минусы**: Высокие капитальные затраты, требует экспертизы.

### Вариант 2: Гибридный (баланс безопасности и стоимости)
- **LLM**: GPT-4 Turbo для общих вопросов, локальная модель для конфиденциальных данных
  - *Причина выбора*: Использовать лучшее качество GPT-4 где возможно, сохраняя безопасность
  - *Железо*: Для локальной части — RTX 4090 или A10
- **Эмбеддинги**: Локальные Sentence-Transformers
  - *Причина выбора*: Все эмбеддинги генерируем локально для конфиденциальности
  - *Железо*: Общее с LLM или отдельный GPU
- **Векторная БД**: ChromaDB
  - *Причина выбора*: Единое хранилище для всех данных
  - *Железо*: Выделенные ноды в EKS
- **Плюсы**: Гибкость, лучшее качество для неконфиденциальных данных.
- **Минусы**: Сложность маршрутизации, зависимость от API.

### Вариант 3: Облачный (минимальные эксплуатационные затраты)
- **LLM**: YandexGPT/OpenAI API
  - *Причина выбора*: Минимальные вложения в инфраструктуру
  - *Железо*: Не требуется (Managed API)
- **Эмбеддинги**: OpenAI Embeddings
  - *Причина выбора*: Интеграция с выбранным облачным провайдером
  - *Железо*: Не требуется
- **Векторная БД**: ChromaDB в облаке
  - *Причина выбора*: Сохранение знакомой технологии
  - *Железо*: Managed service или небольшие виртуальные машины
- **Плюсы**: Быстрое развёртывание, низкие начальные затраты.
- **Минусы**: Данные в облаке, высокая долгосрочная стоимость.

### Вариант 4: Локальный с оптимизацией (рекомендуемый)
- **LLM**: Mixtral 8x7B (4-bit) 
  - *Причина выбора*: Экспертная модель с лучшим качеством среди локально развертываемых, особенно для технических задач
  - *Железо*: NVIDIA A100 (40 GB) или 2× RTX 4090 (через модель параллелизации)
  - *Производительность*: ~20-40 токенов/сек на A100, latency < 2 сек для типовых запросов
- **Эмбеддинги**: e5-large-v2 (Sentence-Transformers)
  - *Причина выбора*: Специализирован для поиска и релевантности, лучше работает с технической документацией чем all-MiniLM
  - *Железо*: Может работать на том же GPU что и LLM (batch-обработка) или отдельном T4
  - *Производительность*: ~1000 документов/мин на GPU для индексации
- **Векторная БД**: ChromaDB с persistent volume в EKS
  - *Причина выбора*: Сочетание производительности, удобства и интеграции с инфраструктурой
  - *Железо*: Выделенные ноды: 16 CPU, 32 GB RAM, 1 TB NVMe SSD
  - *Производительность*: Поиск по 1M векторов за < 100 мс, поддержка 100+ одновременных запросов
- **Инфраструктура**: AWS EKS на:
  - GPU ноды: g5.12xlarge (4× A10G) или p4d.24xlarge (8× A100) для продакшена
  - CPU ноды: r6i.4xlarge для ChromaDB и вспомогательных сервисов
  - Auto-scaling групп для обработки пиковой нагрузки
- **Плюсы**: Баланс качества, безопасности и стоимости; масштабируемость.
- **Минусы**: Требует настройки мониторинга и обслуживания.

## Рекомендации
**Выбор: Вариант 4 (локальный с оптимизацией)**.

**Обоснование выбора конкретных компонентов**:

1. **Mixtral 8x7B вместо Llama 3 8B**:
   - **Причина**: Mixtral имеет в 8 раз больше параметров (47B эффективно), что даёт существенно лучшее качество для сложных технических вопросов
   - **Компромисс**: Требует в 2 раза больше VRAM (но 4-bit квантизация решает проблему)
   - **Железо**: A100 40GB или 2× RTX 4090 через tensor parallelism

2. **e5-large-v2 вместо all-MiniLM-L6-v2**:
   - **Причина**: e5-large специально тренировался для поиска и релевантности, имеет в 2.5 раза больший размер (335M параметров)
   - **Компромисс**: Медленнее и требует больше памяти, но качество поиска критично для RAG
   - **Железо**: Тот же GPU что и для LLM, можно разделять через планировщик

3. **ChromaDB в EKS**:
   - **Причина**: Готовая интеграция с AWS, мониторинг через CloudWatch, backup через EBS snapshots
   - **Масштабирование**: Horizontal Pod Autoscaler + Cluster Autoscaler под нагрузку
   - **Железо**: Отдельная node group с быстрыми SSD и достаточной памятью

**Риски и митигация**:
1. **Экспертиза**: Необходимы специалисты по MLOps и Kubernetes → нанять или обучить 1-2 инженеров
2. **Производительность**: Регулярная оптимизация промптов и чанкирования документов
3. **Обновления**: Механизм переиндексации при изменении документов через CI/CD пайплайны

## Заключение
Для QuantumForge Software рекомендуется развернуть RAG-бота на основе Mixtral 8x7B (4-bit), эмбеддингов e5-large-v2 и ChromaDB в AWS EKS. Эта конфигурация обеспечивает оптимальный баланс между:
- **Качеством ответов** (экспертная модель для технических задач)
- **Безопасностью** (все данные внутри инфраструктуры)
- **Масштабируемостью** (Kubernetes-based архитектура)

Начальная инфраструктура: 2 GPU ноды (A10/A100), 3 CPU ноды, 2 TB быстрого хранилища.
